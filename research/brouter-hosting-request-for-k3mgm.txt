======================================================================
WHAT THIS IS AND WHY
======================================================================
SOTAplanner (sotaplanner.com) helps amateur radio operators plan summit hikes.
Sometimes we know two points (for example two neighboring summits, or a
parking spot and a summit) but have no recorded trail between them, so we
cannot estimate the hike. We want to ask a routing service: "does a walkable
route exist between point A and point B, and if so what is its length, climb
and how much of it is on real paths?"

We will use it three ways:
  1. Gap filling: a hike estimate between two summits in a multi-summit day
     when no recorded track connects them.
  2. Summits with no recorded track at all: a suggested route and estimate
     from the starting point (trailhead or parking) to the summit, clearly
     labelled as a guess.
  3. A "does a hiking path exist?" check: from the answer we tell the user
     whether the route follows trails or is mostly road, or whether no
     route exists at all (an honest "no mapped path" is a useful result).

The tool for this is BRouter, a free, open source (MIT license) route planner
that follows OpenStreetMap trails. The public BRouter server (brouter.de) says
its capacity is very limited, so we would like to run our own copy.

SOTAplanner itself stays where it is (DreamHost). Mark's server would ONLY run
BRouter and answer web requests from SOTAplanner. Nothing else moves, and
Mark does not need access to the SOTAplanner site, code or database.

WHAT WE NEED MARK TO SET UP
======================================================================
1. A Linux server (or VM/container) with:
   - Java runtime (a current LTS version, for example 17 or 21).
   - About 2 GB RAM free for BRouter is plenty; 1 vCPU is enough. On AWS
     that means roughly a t3.small or t4g.small (ARM is fine, Java runs
     on both).
   - Disk: at least 20 GB. NOTE: a default AWS root disk is often only 8 GB,
     which the map tiles alone would fill, so enlarge it when creating the
     server (see COST AND SIZING below).

2. BRouter installed
   - Source and release downloads: https://github.com/abrensch/brouter
     (download the latest release zip; it contains brouter.jar, the standalone
     server scripts and the profiles folder).
   - Run it in standalone server mode, listening only on localhost (for
     example 127.0.0.1:17777, its default port) so it is not directly exposed.
   - Please follow the current README in the repo for the exact start command
     and arguments, since they can change between versions. It takes: the
     segment data folder, the profiles folder, a custom-profiles folder, a
     port and a max thread count. Max threads of 2 to 4 is fine for us.
   - Set it up to start automatically on boot and restart if it crashes (for
     example a systemd service).

3. Map data ("segment" files, .rd5)
   - BRouter routes on prebuilt 5 by 5 degree tiles named by their
     lower-left corner, for example W120_N30.rd5.
   - Download from the BRouter project's segment server:
     https://brouter.de/brouter/segments4/
   - Phase 1 (test): the US West Coast, 10 files, about 392 MB total
     (sizes as listed on the segments page on 2026-10-16):
         W125_N30  1 MB       W120_N30  53 MB
         W125_N35  56 MB      W120_N35  31 MB
         W125_N40  38 MB      W120_N40  21 MB
         W125_N45  67 MB      W120_N45  29 MB
         W125_N50  6 MB       W120_N50  9 MB
     W120_N30 covers longitude -120 to -115 and latitude 30 to 35, which
     includes the Santa Ana Mountains where our first test case is.
   - Phase 2 (goal): worldwide coverage, because SOTA summits exist on every
     continent. We do NOT need all 1,142 files (10.0 GB). The exact list of
     431 tiles to download (every tile with a SOTA summit, plus neighbors for
     routes that cross tile edges) is in APPENDIX A at the end of this
     document, with a ready-to-use download script. It totals 6.86 GB.
     Plan for 15 to 20 GB of disk to leave room for refreshed copies, logs
     and the BRouter install. Download the West Coast test files first
     (those 10 are named in the appendix and are also part of its full list),
     confirm the test route works, then continue with the rest of the list
     (see ORDER OF WORK at the top).
   - The appendix includes a download script that makes both the first
     download and later refreshes easy.

   UPDATING THE TILES
   - The BRouter project regenerates the worldwide tiles weekly (the listing
     showed files stamped 2026-10-16). Our server does not need to keep up
     with that. Trails change slowly, and SOTAplanner caches each routed pair
     permanently.
   - Suggested schedule: refresh about every 3 to 6 months with a cron job
     that downloads only files newer than the local copies. Monthly is fine
     if Mark prefers; weekly is unnecessary.
   - Replace files safely: download to a temporary folder, then move into the
     segments folder, so a half-downloaded file never gets served. A restart
     is not normally needed, but check the README.

4. A hiking profile
   - Routing behavior is controlled by "profile" files. The release includes
     a "trekking" profile, which is what we will start with. We also want a
     hiking-oriented profile (one that prefers footpaths and avoids roads),
     because that is what makes the "does a hiking path exist?" answer
     meaningful. Chris will supply or choose one; Mark just needs to know
     that a profile file is dropped into the profiles folder and BRouter
     picks it up by file name. Please tell us how to add or replace a profile
     (or let us send the file to Mark), since we expect to tune it a few
     times.
   - We will compare results from two profiles on the same pair of points
     (for example trekking vs the hiking one), so both should stay available.

5. A public HTTPS front door (reverse proxy)
   - Put nginx, Caddy or similar in front of BRouter, with a real domain or
     subdomain name and a TLS certificate (Let's Encrypt is fine), for
     example https://routing.sotaplanner.com.
   - Forward only the route path (/brouter) to the local BRouter port. Do not
     expose any other BRouter paths or the raw port.
   - Require a simple shared secret so strangers cannot use it. Easiest:
     the proxy rejects any request that does not carry a header such as
         X-Api-Key: <long random string>
     Mark generates the string and shares it with Chris privately (not by
     email in plain text if avoidable).
   - Rate limit it (for example 30 requests per minute per client) and set a
     request timeout of around 60 seconds.
   - Pass BRouter's response body through unchanged on errors, not just on
     success. When there is no route, or a map tile is missing, BRouter
     answers with a short plain-text message and an error status. We need to
     read that message to tell "no path exists" apart from "server problem".
   - Firewall (on AWS, the security group): allow inbound 443 (and 80 if
     needed for certificate renewal), and SSH from Mark's own addresses only.
     The BRouter port itself (17777) must NOT be open to the internet.

COST AND SIZING (AWS)
======================================================================
Prices below are approximate, from memory of AWS's public price list in a
main US region. Please check the current AWS pricing page before relying on
them; they vary by region.
 - Disk (EBS gp3, about $0.08 per GB per month): 20 GB is about $1.60 a month.
   Even if Mark wants more headroom, 30 GB is about $2.40 a month. Disk is
   billed for the size of the volume, not how full it is.
 - Data in: free. Downloading the tiles from brouter.de costs nothing.
 - Data out: SOTAplanner's responses are small route files and the load is
   low, so this should stay far inside AWS's free monthly outbound allowance
   (about 100 GB). Even the bulk runs described below add very little.
 - Compute: this is the real cost. A small always-on server (t3.small or
   t4g.small, 2 GB RAM) is roughly $12 to $15 a month, less with a reserved
   or savings plan. If Mark already runs a server with room to spare, running
   BRouter there adds almost nothing apart from the 20 GB of disk.
 - Cheaper idea if cost matters: stop the server when not needed. We do not
   mind if it is down some of the time (see "Uptime" below). Though note
   SOTAplanner shows "no estimate" for any leg requested while it is off.
 - Total, rough estimate: about $15 a month for a dedicated small server, or
   about $2 a month if it shares one Mark already has.
 - Chris pays the AWS costs. Mark just needs to tell Chris if the bill ever
   looks different from the estimate.

WHAT SOTAPLANNER WILL CALL
======================================================================
One simple web request, made by the SOTAplanner server (PHP), never from a
visitor's browser:

   GET https://routing.sotaplanner.com/brouter
       ?lonlats=-117.544,33.7201|-117.5342,33.7107
       &profile=trekking
       &alternativeidx=0
       &format=geojson
   Header: X-Api-Key: <the shared secret>

Notes:
 - lonlats is LONGITUDE first, then latitude. Points are separated by a pipe
   character (sent URL-encoded as %7C).
 - profile is the profile file name (trekking now, a hiking profile later).
 - format=geojson returns the route line plus totals (distance in meters,
   climb, time). format=gpx is also available.
 - We need the per-segment "messages" table that BRouter adds to the geojson
   (it lists each stretch of the route with its OpenStreetMap way tags, such
   as highway=path or highway=track). That is how we measure how much of the
   route is on real trails vs roads. Please confirm the test command below
   returns it, and tell us if it needs a setting or profile option.
 - Point pairs are usually straight from summit to summit or trailhead to
   summit, 2 points per request. Distances are mostly under 20 km, but some
   multi-summit days or remote summits may run to 50 to 100 km. Please do not
   cap distance below that if BRouter allows it.
 - We may occasionally ask for alternative routes (alternativeidx=1, 2, 3) to
   compare against the first.
 - Expected load, normal use: low. A handful of requests a day, because
   SOTAplanner caches every result permanently (each pair is asked once).
 - Expected load, bulk runs: the "summits with no recorded track" use means
   we may someday sweep a large list of summits in the background, from a
   scheduled job on our side. That would be sequential (one request at a
   time) with a pause between requests, up to roughly 10 to 20 requests per
   minute, running for hours or days at a time, and we would start with one
   region (for example Southern California) before anything larger. Mark,
   please tell us what rate and time of day you are comfortable with, and
   we will set our job to stay under it. We can stop it instantly.
 - Typical response time for a few miles of trail: well under a second after
   BRouter warms up; longer routes can take several seconds.

DOWNLOAD / REFRESH SCRIPT (suggested; adjust paths)
 Save the file names from the table below, one per line, as tiles.txt (just
 the first column plus ".rd5", for example "W120_N30.rd5"). Then:

   #!/usr/bin/env bash
   set -euo pipefail
   BASE=https://brouter.de/brouter/segments4
   SEG=/var/lib/brouter/segments4            # BRouter's segment folder
   TMP=/var/lib/brouter/segments4.incoming   # same filesystem as $SEG
   LIST=/var/lib/brouter/tiles.txt
   mkdir -p "$SEG" "$TMP"
   while read -r f; do
     [ -z "$f" ] && continue
     # -z: only download if the server copy is newer than ours (a 304 gives an
     # empty file, which we discard). -R: keep the server's timestamp so -z
     # works on the next run.
     if ! curl -sS -f -R --retry 3 --retry-delay 10 -m 1800 \
          -z "$SEG/$f" -o "$TMP/$f" "$BASE/$f"; then
       echo "FAILED $f"; rm -f "$TMP/$f"; continue
     fi
     if [ -s "$TMP/$f" ]; then mv "$TMP/$f" "$SEG/$f"; echo "updated $f"
     else rm -f "$TMP/$f"; fi
     sleep 2
   done < "$LIST"

 Verify afterwards: the number of .rd5 files in the segment folder should be
 431 and the folder should total about 6.9 GB. Each file's size should match
 the size in the BRouter listing page. A half-downloaded file (the script only
 moves complete downloads into place) must never sit in the live folder.

 A refresh as a cron job (for example the 1st of every third month, run at
 night) is enough. No BRouter restart is normally needed, but check the
 README for the version installed.
